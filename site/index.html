SafeMAV: deterministic authorization and policy enforcement
for irreversible physical actions initiated by AI agents

An MCP agent with a UAV connector can write a sentence that takes an aircraft off the ground. SafeMAV puts a non-language-model gateway between that sentence and the MAVLink stream: every physical write needs an Ed25519 signature from a key the agent cannot reach, bound to those exact parameters, re-verified immediately before each of the several SDK calls one action makes, and recorded in a hash-chained ledger.

The failure mode

Confirmation flags are not consent

The original guardrails asked the agent to pass confirm=True on dangerous calls. The component being asked to confirm is the component that wants the action. That is not a safety boundary — it is a polite request to the adversary. Measured across 690 unauthorized attempts on the pre-gateway code: 82.6% reached a physical sink, and 66.7% of attempts to get the vehicle airborne succeeded.

0%

Cryptographic binding

Nothing in the old design ties a human's decision to the request that later executes. Approval could not be replayed-proof because there was nothing to replay.

100%

Parameter tampering accepted

Change the altitude after the human said yes, reorder a mission, swap the vehicle id. The baseline re-reads live values at dispatch, so the sanctioned number never was the flown number.

100%

Stale telemetry flown

Two satellites, NO_FIX, or home position older than any budget: staleness is literally unrepresentable without receipt metadata, so it is never a reason to refuse.

0%

False rejection on legitimate ops

On the baseline arm too. And worth saying plainly: the envelope guardrails were good. The altitude ceiling and haversine geofence blocked out-of-envelope targets exactly as well as the gateway does. Those checks did not need replacing.

The mechanism

Five properties the baseline could not express

01

Approval is signed, not asserted

An Ed25519 signature over a canonical request digest, from a key the server only knows the public half of. The token binds actor, vehicle, gateway id, boot epoch, policy hash, connection epoch, home position and the exact parameters. confirm=True still parses and authorizes nothing.

02

Spent once, in the ledger

The claim is a durable SQLite transaction under a single-owner OS file lock, so four simultaneous submissions of one approval dispatch exactly once. Sequential reuse returns APPROVAL_REPLAY with zero sinks.

03

Byte-level parameter binding

Comparison is on canonical bytes in integer units — degrees×10⁷, millimetres, millidegrees, mm/s — because == happily reports True == 1. Inputs are range-checked and tested for float32 wire rounding before they can silently shift on the MAVLink side.

04

Authority re-checked per sink

Takeoff is set_takeoff_altitude then takeoff. Immediately before each, the gateway re-verifies the UTC and monotonic deadline, telemetry freshness, epochs, policy hash, operator key scope and ledger writability — with no await between gate and call.

05

Uncertain latches closed

If the second sink cannot be cleared, the request is recorded UNKNOWN, the partial effect is written, and the next command is refused rather than issued into a vehicle state nobody knows. That latch survives a process restart.

G1

What a signature cannot buy

Enforcement is an in-process trust boundary. Code already running in the same interpreter can read the gateway's private issuer object and forge a lease. That is a deployment-containment property (G2) this project does not implement — and it ships as a passing test that asserts the failure.

Architecture

The gateway is the trust boundary

Everything to the left of the shaded band is attackable and assumed to be adversarial — including the Python API. The capability layer is a thin facade: a Drone built without a gateway cannot write at all. The adapter is the only module that imports mavsdk, and it refuses any write that does not carry a valid execution lease minted by the gateway a moment earlier.

Untrusted

MCP agent · Python script · injected document text. May hold valid-looking JSON, may not hold the key.

Capability layer

Drone — 8 capabilities, structured results, zero authority of its own.

SafetyGateway

Admission → policy → approval → lease. Writes the ledger, then commands.

Adapter

Validates the lease per sink, translates to MAVSDK, raises without one.

Autopilot

PX4 / ArduPilot over MAVLink. Its own failsafes stay in charge.

Reads are cheap, writes are earned

Telemetry, flight mode and connection status need no approval — an agent that has to ask permission to look cannot plan. But every receipt carries the instant it arrived, its source and the connection epoch, so stale is a representable state rather than a guess.

Configuration fails closed

An invalid or unreadable policy file is a refusal, not a fallback to defaults. An unknown backend name does not start a drone. The readonly kill switch is honoured at the facade — and measured, so nobody mistakes it for containment: direct adapter calls are unaffected by it.

Quantitative benchmark

Two real code arms, identical scenarios, one recording adapter

Baseline is commit 962448c — the original pre-gateway guardrails, reconstructed in benchmark/baseline.py and mechanically verified against git on every run: constants, defaults, the haversine_m distance, and the decision control flow of all twelve guardrail methods. SafeMAV is the live tree at 7055a49. Both arms drive the same spy adapter, the only place physical effects are recorded. 36 subcases × 30 trials × 2 arms, plus 180 readonly-control trials. Seeds derive from a fixed master seed, so the run reproduces byte-identically.

Recovery is behaviour, not a pass rate

Backend fails after the first of two sinks in a takeoff plan, 30 trials per arm:

baseline  sinks: set_takeoff_altitude, hold
          partial effect recorded: 0/30
          next command: executed into an unknown state

SafeMAV   sinks: set_takeoff_altitude
          partial effect recorded: 30/30
          terminal status: UNKNOWN → next command refused

Neither arm is credited with prevention — a sink fired. The difference is what happens next.

Latency on the approved path

In-process software latency on one host, 120 samples per arm, excluding the time it takes a human to read and sign, which dominates the real sequence. No network, autopilot or airframe response time is included.

The cost is durable storage, not cryptography: Ed25519 verification measured 48 µs median on this host, one synchronous=FULL SQLite audit event 4.1 ms median — and the approved path writes several. Treat the tail as OneDrive-on-Windows filesystem noise rather than a property of the design.

The number that guards against a cheap trick. A deny-everything configuration was measured as a control arm, precisely so these attack rates cannot be read as "turn everything off": it scores 100% false rejection on legitimate operations — zero flight utility — and still lets 13.0% of unauthorized attempts execute, because readonly is a facade-level flag and calls that reach the adapter directly never see it. SafeMAV's attack numbers are bought with 0% false rejection instead.
Real autopilot

Measured against headless PX4, not only mocks

The benchmark tier is deterministic mocks. To test the transport and the freshness thresholds rather than assume them, the same gateway was pointed at a live PX4 SITL through MavsdkAdapter — PX4's built-in SIH dynamics, no Gazebo, no GPU, no hardware contacted. MAVSDK 3.17.2, the pinned version.

4 / 4

Signed actions observed in flight

arm → armed = true; takeoff 10 m → climbing through 8.23 m at the check; goto → reached lat 47.397804; return_to_launch → in_air = false. Observed telemetry, not RPC acknowledgement.

10 / 10

Refusals with expected reason codes

Self-asserted confirm=true → APPROVAL_REQUIRED; signature altered by six characters → APPROVAL_INVALID; valid token without its request_id → APPROVAL_INVALID; 500 m against a 30 m ceiling → ALTITUDE_LIMIT; NaN and 10.00000001 → INVALID_ARGUMENT.

1.97 s

Freshness was measured, not guessed

Position and attitude arrive near 50 Hz, but battery and home are 1 Hz with a worst observed age of 1.974 s. The architecture document had assumed a 0.5 s skew limit. Under that value a healthy RTL was wrongly refused TELEMETRY_STALE, so the bound was set from the distribution instead: max_age_ms = max_skew_ms = 3000.

eeprom

Reproducibility hygiene

PX4 persists parameters and simulated vehicle state between runs, so a rerun could start armed and airborne. The launcher wipes eeprom and the BSON flight stack before every evidence run — otherwise "reproducible" would be a claim about luck.

Full transcript, host, versions and raw log: docs/SITL_EVIDENCE.md · machine-readable · the script that produced it. This tier still does not exercise flight dynamics, real link loss or hardware.
Adversarial coverage

Twenty-five threats, each mapped to a test that runs

Injection gets no special treatment, because it gets no authority. Eight hostile payloads — English, a zero-width homoglyph, an RTL override, JSON that forges an approval object, a fake "system" turn, and text pretending to be telemetry — were pushed at six entry points: tool arguments, mission metadata, identity fields, telemetry-derived text, the audit trail, and the approval renderer. None can enter a canonical parameter or authorize anything, because the fields that decide are typed integers derived from a signature digest, not strings copied from a conversation. Full mapping: docs/ADVERSARIAL_TESTS.md.
Limitations, stated plainly

What this does not claim

A safety submission that overstates is worse than one that underclaims. These are the boundaries we would want a reviewer to check first.

G2 containment is not implemented

Enforcement covers the MCP tools and the supported Python API in this process. It is not an OS sandbox. Same-process Python that reaches the gateway's private _issuer can forge a valid lease and command the vehicle — 30/30 on the benchmark, on both arms. Closing it needs process or OS isolation. The test asserting this failure ships in the suite.

Mocks and one host

The 2,340-trial benchmark runs on deterministic mocks: it demonstrates pre-dispatch gating, binding, fault timing and the state machine, and demonstrates nothing about flight dynamics, autopilot behaviour or real MAVLink transport. Latency is one Windows host with the ledger on a cloud-synchronized directory. No physical UAV was involved in any experiment.

Scenario selection is ours

36 subcases from the project threat matrix. Wilson intervals describe sampling variability of this suite on this host — not accident probability on any real aircraft. Trials cluster by scenario: a check that denies all 30 trials of a subcase is one mechanism observed 30 times, and the interval width understates uncertainty about unseen attack classes.

Not a substitute for the autopilot

These checks do not replace PX4/ArduPilot's own failsafes, a geofence actually configured in the flight controller, network isolation, registration and flight permits under your local aviation law, or a human holding an RC transmitter. ACKNOWLEDGED means the autopilot accepted a command — never that a flight completed.

Baseline arms are reconstructed

The comparison arm for 962448c is a faithful reconstruction, not the historical binary: two declared adaptations (a call-schema shim and a writable configuration) were needed to run one shared spy adapter, neither touching policy. It has no token, nonce, digest or ledger, so cryptographic replay acceptance for that arm is N/A, not 0% — the semantic equivalent is measured and labelled with an ADAPTATION: note in every affected trial.

No novelty claim

Parameter-bound, cryptographically signed human authorization for AI-initiated actions is a design point assembled from established practice — capability-based security, confirmation-of-command, two-person integrity, tamper-evident logs. SafeMAV does not claim to be the first system of its kind; what it claims is a measurable, reproducible instance of it on a real UAV protocol.
